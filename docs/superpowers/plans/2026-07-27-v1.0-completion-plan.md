# Missile Defense 1.0 Completion Plan

**Status:** Canonical execution plan for 1.0  
**Updated:** 2026-07-27  
**Product goal:** A fun, self-directed way to learn how machine learning works by
training, observing, diagnosing, and challenging an AI in a real game.

This plan supersedes the completion status and delivery order in
`2026-07-26-ai-training-user-journey.md`. That document remains the detailed
design and implementation record. The approved user-journey design remains the
product specification; this document closes the gaps between the current branch
and a polished 1.0.

---

## 1. The 1.0 promise

Missile Defense is not merely a game with an attached training dashboard. A
first-time user should be able to learn, without a terminal:

1. what an observation, action, policy, reward, episode, and update are;
2. why training return and game score are different;
3. why evaluation uses held-out seeds and identical conditions;
4. how exploration, learning rate, reward design, architecture, and training
   time change behavior;
5. how to diagnose a plateau from both statistics and visible play;
6. why one result is not evidence, and how a fair multi-seed comparison works;
7. how to promote a checkpoint and challenge another policy reproducibly.

The core learning loop is:

> **Predict → change one thing → train → watch → measure → explain → challenge**

Every primary screen and action must support that loop. Advanced controls may
remain available, but the default journey teaches rather than presenting an
unexplained wall of parameters.

### Definition of “fun”

The app should provide short goals, visible progress, satisfying game playback,
and meaningful challenges. It must not fake learning progress, hide unfavorable
results, or turn educational concepts into arbitrary points and badges. The fun
comes from making a prediction, seeing a policy acquire a behavior, and then
putting that behavior into a fair contest.

---

## 2. The skill ladder

The scripted agents are a learning ladder, not three equivalent “baselines”:

| Level | Canonical mean score | Meaning in the journey |
|---|---:|---|
| **LOW** | 19,585.5 | First target; demonstrates wasteful duplicate firing |
| **MEDIUM** | 63,295.6 | The benchmark a trained relational policy should beat clearly |
| **HIGH** | 98,542.3 | The challenge target and current expert reference |

The bundled learned policy scores **90,865.9** on the same held-out 32-seed
protocol. It easily beats MEDIUM and approaches HIGH. That is a successful,
understandable progression: it learned most of the ammunition discipline but
still wastes more shots than HIGH.

1.0 must not claim that the learned policy already beats HIGH. HIGH is the
aspirational challenge. The UI should celebrate beating LOW and MEDIUM, show the
remaining behavioral gap to HIGH, and invite the user to close it.

All displayed comparisons must name the seed split, number of episodes, game
configuration, decision rate, and whether the result is quick/unranked or
canonical/ranked.

## 4. Scope that must ship before 1.0

The following previously planned work is confirmed as pre-1.0 scope:

- the complete guided learning journey and training curriculum;
- Model League evaluation and head-to-head UI;
- paired recordings and synchronized split-screen match spectating;
- cleanup, archive, verify, restore, model export, and model import UI;
- durable compatibility metadata for runs, models, matches, and archives;
- replay discovery and ordering fixes;
- a single accurate documentation set for the installed UI journey;
- zero Vulkan validation errors and warnings, with shader and runtime checks in
  the normal tools/CI gates;
- installed-package end-to-end tests and human acceptance on the supported
  platform matrix.

Optional round-robin leagues, cloud training, multiplayer, user-authored Python
agents, recording continuous human mouse input, and online accounts/telemetry
are not required for 1.0.

## 5. Workstream A — Make learning the primary journey

### A1. Guided start

- [ ] Replace the parameter-first new-run experience with three clearly labeled
      paths:
  - **Learn** — recommended guided lessons;
  - **Experiment** — choose a preset and change one variable;
  - **Advanced** — the full existing parameter editor.
- [ ] Add a brief, skippable introduction that connects the game's visible
      problem to observation, action, reward, policy, and episode.
- [ ] Before each experiment, ask the user to choose or write a prediction. Show
      that prediction beside the result; never grade it as “wrong.”
- [ ] Keep a local experiment notebook that ties each run to its question,
      prediction, changed variable, result, user observation, and next idea.
      Generate the facts automatically but let the learner write the conclusion.
- [ ] Keep explanations beside the relevant control or chart, in plain language,
      with a deeper “Why?” disclosure.
- [ ] Persist lesson progress and the last meaningful next step locally. The app
      remains fully usable offline and collects no telemetry.

### A2. A small 1.0 lesson sequence

- [ ] **Lesson 1 — Watch three strategies:** spectate LOW, MEDIUM, and HIGH;
      identify duplicate shots and connect them to wasted-shot statistics.
- [ ] **Lesson 2 — What training changes:** run a short, bounded training preset;
      see episodes, updates, exploration, and the distinction between reward and
      game score.
- [ ] **Lesson 3 — Change one thing:** choose learning rate or entropy from three
      explained values, predict the effect, and compare against the untouched
      run.
- [ ] **Lesson 4 — Represent the problem:** compare MLP and entity/relational
      presets, explaining why variable collections of threats are different from
      a flat list of numbers.
- [ ] **Lesson 5 — Generalize and challenge:** select a checkpoint on validation
      seeds, evaluate once on held-out seeds, promote it, beat LOW/MEDIUM, and
      attempt HIGH.
- [ ] End each lesson with one observation prompt and a concrete next experiment,
      not a generic “completed” screen.

The lesson copy must be reviewed against the actual implementation. It must not
imply that PPO guarantees improvement, that a short run will beat a fixed score,
or that a single seed establishes superiority.

### A3. Honest pacing

- [ ] Benchmark lesson presets on the minimum supported CPU and a reference GPU.
- [ ] Show an estimate before starting: wall time range, disk use, backend, and
      expected educational outcome.
- [ ] Provide a genuinely short first experiment. If meaningful score movement
      cannot be produced quickly on minimum hardware, use an included completed
      run for the observation lesson and clearly distinguish it from the user's
      subsequent real training.
- [ ] Add pause-safe, crash-safe resume and actionable out-of-space handling to
      every lesson path.
- [ ] Let users skip waiting by opening existing recordings and explanations
      while training continues out of process.

### Acceptance

- [ ] A new user can complete the first useful learning loop without a terminal,
      documentation, or unexplained required choice.
- [ ] In a short moderated test, the user can correctly explain at least:
      observation/action/reward, training versus evaluation, and why identical
      seeds matter.
- [ ] The user always knows what is running, why it is running, how long it may
      take, what changed, and what to try next.

## 6. Workstream B — Make training progression real

- [ ] Implement the M6 training curriculum instead of starting every policy at
      full game difficulty. Define stages in data, with explicit advancement
      criteria, recorded stage transitions, and a way to disable curriculum for
      controlled experiments.
- [ ] Use the best-supported entity/relational architecture for the recommended
      path. Keep MLP as an educational comparison, not an unexplained default
      that is known to plateau.
- [ ] Define and benchmark **Quick lesson**, **Standard**, and **Challenge**
      presets. Store the complete resolved configuration in the run manifest.
- [ ] Display which settings differ between two runs. Warn when a comparison
      changes multiple causal variables.
- [ ] Annotate curves with resume points, curriculum changes, parameter changes,
      best-checkpoint selection, and evaluation events.
- [ ] Explain validation selection and make the one-time canonical held-out
      evaluation an explicit action. Do not leak held-out results into automatic
      checkpoint selection.
- [ ] Calibrate expected progression. LOW should be reachable by the guided
      path, MEDIUM should be the demonstrated normal target, and HIGH remains the
      open challenge; stochastic runs must be described with ranges rather than
      guarantees.
- [ ] Add tests for curriculum advancement, resume, reproducibility, config
      persistence, split isolation, and preset migration.

### Acceptance

- [ ] The recommended path demonstrates a visible behavioral improvement, not
      only a changing loss curve.
- [ ] Every score in the console can be traced to a complete evaluation protocol.
- [ ] Repeating a recorded experiment configuration is possible from the UI.

## 7. Workstream C — Finish fair competition and spectating

- [ ] Finish the Model League actions: Evaluate, Head to head, contestant
      selection, progress/cancel, result cards, history, and compatibility
      explanations.
- [ ] Rank only complete canonical evaluations. Label quick results prominently
      as unranked and never silently replace a canonical result with a partial
      run.
- [ ] Generate an action log for both contestants on every selected paired seed,
      checksum both recordings, and write an atomic match manifest.
- [ ] Finish `md_app --match <manifest>` with two rendered viewports, shared
      transport, per-side identity/score, seed and protocol, live score delta,
      and a frozen final state when one side ends first.
- [ ] Support pause, speed, seek, restart, expand either side, unequal endings,
      and corrupt/missing-side errors without desynchronization.
- [ ] Add **Watch match** from the league and an installed game exhibition of
      bundled learned versus scripted HIGH.
- [ ] During and after a match, explain the most relevant behavioral difference,
      such as wasted shots, kills per shot, base/city loss, or survival time.
- [ ] Complete native, Python, app E2E, and installed-package tests for fairness,
      cancellation, atomic results, and synchronized playback.

### Acceptance

- [ ] A user can promote two models, compare them on identical seeds, watch both
      policies play the same seed side by side, and understand why one won.
- [ ] Rankings are reproducible and never mix incompatible simulator,
      observation, action, policy, or evaluation versions.

## 8. Workstream D — Make artifacts durable and understandable

### D1. Compatibility contract

- [ ] Give runs, promoted models, matches, recordings, and archives versioned
      manifests containing, as applicable:
  - stable ID and editable display name;
  - app/build version and creation time;
  - simulator/config schema and deterministic-logic compatibility ID;
  - observation and action schema IDs;
  - architecture and native policy-format version;
  - curriculum, resolved training config, seed splits, and evaluation protocol;
  - parent run/checkpoint/model IDs;
  - file sizes and cryptographic checksums;
  - replay/match compatibility and archive schema version.
- [ ] Reject unsupported or corrupted artifacts before registration or playback
      with an actionable message. Never guess compatibility from a filename.
- [ ] Define migrations for metadata that can be migrated safely; preserve and
      clearly label data that can only be viewed by an older build.

### D2. User-facing lifecycle

- [ ] Complete cleanup UI with category counts, exact reclaimable bytes, and a
      dry-run plan. Protect active files, summaries, best/promoted checkpoints,
      and pinned recordings by default.
- [ ] Complete archive UI: choose contents, show estimated size, write, checksum,
      verify, and only then enable **Remove original**.
- [ ] Restore only into a new destination, using safe extraction and atomic
      registration. Never overwrite an existing run.
- [ ] Complete model `.mdp` export/import with metadata, checksum, dimensions,
      schema, and native inference validation before league registration.
- [ ] Add storage forecasts and low-disk warnings before training, plus recovery
      guidance after interruption.
- [ ] Prove archive round trips preserve curves, configurations, evaluations,
      models, and selected recordings.

### Acceptance

- [ ] A user can see what consumes space, reclaim the promised amount safely,
      move a complete experiment, restore it, and understand whether it is
      compatible.
- [ ] No cleanup, archive, restore, or import failure can leave a half-registered
      artifact or delete the only valid copy.

## 9. Workstream E — Fix replay discovery

The current game browser only scans `.mdr` files directly inside the runs root,
while managed runs store recordings in per-run directories. It also sorts file
paths and display names independently, which can associate a label with the
wrong recording.

- [ ] Discover recordings under managed run directories using the same storage
      contract as the console. Do not follow links outside the managed root.
- [ ] Store path, display label, run identity, update, timestamp, and
      compatibility as one record and sort the records once, newest first.
- [ ] Show the run/model name and a useful episode label rather than deriving
      identity only from the filename.
- [ ] Handle an active write, deleted file, incompatible recording, empty
      library, and corrupt recording without crashing or displaying stale data.
- [ ] Test nested discovery, ordering, label/path association, rescanning,
      containment, incompatibility, and launching the selected file.
- [ ] Cover the fixed flow in the real-app E2E suite.

### Acceptance

- [ ] Every playable recording visible in the console is discoverable from the
      game, and selecting a displayed label always opens that exact recording.

## 10. Workstream F — Zero-warning Vulkan correctness

Two Vulkan validation VUIDs are currently allow-listed in the app E2E harness.
That is not acceptable for 1.0, even if one originates in a framework, loader,
or overlay rather than project shader source.

- [ ] Reproduce each current VUID in a controlled environment and record the
      smallest scenario, layer/loader versions, driver, and ownership evidence.
- [ ] Resolve the root cause through application synchronization/lifetime fixes,
      a supported Qt/loader/driver pin or upgrade, or removal/isolation of an
      offending injected layer. Do not suppress the message.
- [ ] Delete `KNOWN_VALIDATION_ERRORS`; no Vulkan error or warning baseline is
      allowed at release.
- [ ] Add a cross-platform `poe vulkan-check` task that:
  - validates generated SPIR-V with `spirv-val` for the declared Vulkan target;
  - starts the debug app with `VK_LAYER_KHRONOS_validation`;
  - enables synchronization and best-practices validation where supported;
  - exercises menu, gameplay, scripted/learned watch, replay, takeover, and
    split-screen match scenarios;
  - fails on every validation warning or error and prints the complete message.
- [ ] Put the static shader check in `poe check`; put the runtime scenarios in
      `poe check-all`. Make both mandatory in release CI.
- [ ] Run the controlled CI check on a deterministic software Vulkan driver and
      smoke-test supported hardware vendors/platforms before release.
- [ ] Document the exact SDK/layer versions used by CI so a local result is
      reproducible.

### Acceptance

- [ ] The source tree, clean local gate, and release CI contain no Vulkan
      validation errors or warnings, no VUID allow-list, and no unvalidated
      checked-in/generated shader.

## 13. Release gates

### Automated

- [ ] `poe check` passes from a documented clean environment.
- [ ] `poe check-all` passes, including zero-warning Vulkan runtime validation.
- [ ] Debug and Release C++ tests, Python tests, strict types, lint, format,
      clang-tidy, and coverage pass without suppressing new warnings.
- [ ] The full installed-user E2E performs: install → guided lesson → short real
      run → replay → promote → fair head-to-head → split-screen match → cleanup
      dry run → archive → verify → restore → imported-model validation.
- [ ] Game-only packages contain both bundled agents and no Python/training
      dependency.
- [ ] Full packages expose the console directly and from **TRAIN AI**.
- [ ] Debian’s package split and Windows/macOS/Linux install/upgrade/uninstall
      matrices pass on the declared supported versions.
- [ ] Artifact corruption, traversal, links, oversized declarations,
      incompatibility, partial writes, and existing restore targets are rejected
      without data loss.

### Human acceptance

- [ ] M2, M3, and M4 receive the roadmap’s required human sign-off.
- [ ] A fresh-user learning session validates the acceptance criteria in A.
- [ ] A complete no-terminal journey is performed from each supported packaged
      build, not only from a source checkout.
- [ ] Visual/audio polish, controls, help text, lesson pacing, match readability,
      and failure recovery are reviewed on real hardware.

### Release decision

1.0 is ready only when every pre-1.0 item in this plan is complete, the automated
release gates are green, supported packages have been exercised, and the human
acceptance gates are recorded. A passing unit suite alone is not a release
decision.

## 14. Recommended delivery order

1. Fix replay discovery and remove current correctness/documentation
   contradictions.
2. Specify lesson outcomes, curriculum stages, and honest preset budgets.
3. Implement the guided learning path and curriculum.
4. Finish league evaluation, paired artifact generation, and split-screen UI.
5. Finish artifact manifests and the cleanup/archive/import/export UI.
6. Resolve Vulkan diagnostics and make the new checks mandatory.
7. Complete accessibility, recovery, documentation, and packaging integration.
8. Run clean automated gates, packaged end-to-end journeys, learning usability
   acceptance, and milestone sign-offs.

Each slice lands with focused tests, updated user-facing copy, and an executable
acceptance scenario. Backend completion without its user journey does not close
a 1.0 item.
